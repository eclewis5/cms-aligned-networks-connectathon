Connectathon / Scenarios

Scenarios

Each scenario tests one requirement from the "Requirements for all Networks" section of the GA Requirements. Run them in pairs, between two CMS aligned networks, and record every run.

Exact message formats, endpoints, and test patient data are TBD and will be published with the test tools. Pass criteria below come directly from the GA requirement text.

Minimum scenarios

Minimum

N1 Patient matching

GA requirement
Patient Matching: incorporate CMS-approved patient matching logic on a CMS aligned network.
What happens
Network A sends a query for a synthetic patient to Network B using different combinations of identifying data from the CMS patient matching proposal (v3.2.2).
Pass when
  • A query that matches under any of the 27 combinations gets a response from Network B, subject to applicable law.
  • A query that matches no combination does not return another person's data.
Needs
Synthetic patients and the 27 combinations (test data TBD).
Minimum

N2 Purpose of Use handling

GA requirement
Purpose of Use: handle purpose of use and respond to requests for patient access, treatment, payment, and operations.
What happens
Network A sends one query per purpose using the HL7 Purpose of Use codes: PATRQT (patient access), TREAT (treatment), HPAYMT (payment), HOPERAT (operations), and HQUALIMP (quality improvement).
Pass when
  • The declared Purpose of Use travels with the request to the downstream system.
  • Network B applies the disclosure rules for that purpose and responds accordingly.
  • A request with no declared Purpose of Use is rejected.
Minimum

N3 Dynamic Client Registration

GA requirement
Dynamic Client Registration: support Dynamic Client Registration using CMS-approved software statements.
What happens
A client registers with Network A, then registers with Network B using the same credentials, once with a CMS-signed software statement (Medicare App Library app) and once with a UDAP software statement (other participant type).
Pass when
  • Both networks accept a valid CMS-signed software statement for Medicare App Library apps.
  • Both networks accept a valid UDAP software statement for all other participant types.
  • The client is accepted by the second network without redundant onboarding or duplicate trust requirements.
  • An invalid or unsigned statement is rejected.
Note
Manual registration was allowed only through October 1, 2026. Dynamic Client Registration is now the primary onboarding mechanism.
Minimum

N4 Data querying, structured and unstructured

GA requirement
Data Querying: respond to or facilitate response to queries with all data requested, subject to HIPAA minimum necessary and applicable law.
What happens
Network A queries Network B for a synthetic patient whose record includes encounters, USCDI v3 data, a scanned PDF, and an image.
Pass when
  • The response includes structured data (USCDI v3) and unstructured artifacts (PDFs, scans, images), not structured data alone.
  • Everything responsive to the request and permitted for the declared Purpose of Use is returned.
Minimum

N5 Audit logging

GA requirement
Auditability: networks produce audit logs for queries on their network showing where patient data was shared, with whom, when, and for which Purpose of Use, retained for at least 7 years.
What happens
After running N1 to N4, each network produces its audit log for the test queries.
Pass when
  • Each query has a log entry showing who accessed or received the data (organization level at minimum), when, and the declared Purpose of Use.
  • Participant-supplied access events appear in the network log.
  • The network states its retention period, which must be at least 7 years.
Note
Retention is verified by attestation. It can't be tested in one day.

Advanced scenarios

Advanced

A1 Record location (RLS)

GA requirement
RLS: networks should participate in CMS-approved record location mechanisms that identify where records exist before broad queries.
Pass when
A request to the Record Locator Service from a patient, provider, payer, or value-based care organization returns the locations of a synthetic patient's records, and the follow-up queries go only to those locations.
Advanced

A2 National Provider Directory publishing and usage metrics

GA requirement
Provider Directory Publishing and Usage Metrics: publish the directory of providers on the network and usage stats by provider for each use case to the National Provider Directory.
Pass when
  • Participants, stable endpoints, and NPI-level metadata (or organization-level metadata if NPI is unavailable) are published to the directory.
  • Usage metrics are reported per provider for patient, treatment, payment, and operations queries.
  • A change to a provider's information flows through on the agreed update cadence, and incorrect information can be flagged.
Needs
The NPD specifications pinned in the provider directory channel on the CMS Health Tech Ecosystem Slack.
Advanced

A3 Response for patient, provider, and payer use cases

GA requirement
Data Response for Use Cases: respond to queries for all three use cases (patient, provider, payer) if available on the network.
Pass when
  • A patient-initiated query using an IAL2 credential is answered, with no portal login and no extra identity steps.
  • A provider treatment query is answered with clinical and claims data.
  • A payer query for clinical data supporting a claim from the last 60 days is answered by a query response, not a proactive push.
  • No use case adds friction, delay, or special process for the requester.
Advanced

A4 Honoring disclosure restrictions

GA requirement
Data Querying: networks must honor agreed-upon restrictions on disclosure (for example, 45 CFR 164.522, including out-of-pocket payment restrictions).
Pass when
For a synthetic patient with a restriction on file, a payment or operations query does not return the restricted data, while the same patient's other data is returned normally.

Not tested at the event

  • HITRUST certification. Required of every CMS aligned network. Confirmed by attestation, not by a test run.
  • Rules of the Road. Maintained by the HTE community. Networks are expected to adhere to them, but there's no scenario for this.
  • Electronic personal representative authentication. Not solved at the network layer in the current GA. Participants keep using their existing HIPAA-compliant processes.
