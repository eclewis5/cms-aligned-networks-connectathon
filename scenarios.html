Connectathon / Scenarios

Scenarios

Each scenario tests one network requirement. Run them in pairs, between two CMS aligned networks, and record every run.

Requirements are taken from the CMS-Aligned Network Specification (can-spec/0.6, an editor's draft), cited below as "§". Where the specification and the CMS Interoperability Framework differ, the Framework controls. Message formats, endpoints, and test patient data are TBD and will be published with the test tools.

How to read a scenario

  • Spec names the specification sections the scenario tests. Read them first.
  • Pass when lists what the specification requires. A scenario passes only if every item is met.
  • Also check at the event lists things we look at to make the test useful. They are reasonable expectations, not stated in the specification word for word.
  • Several parts of the specification are still open. Where a scenario touches one, it says so, and the result is recorded as a finding rather than a failure.

Minimum scenarios

Minimum

N1 Patient matching

Spec
§6 Patient Matching. §5.2 Pathway 2, RLS Network Search ($match). The field list and combination matrix are in the CMS Patient Matching Proposal (v3.4.0), which the specification incorporates by reference.
What happens
Network A sends a FHIR Patient $match request for a synthetic patient to Network B's RLS endpoint. Repeat with different combinations of identifying data from the proposal, including combinations that should match and ones that should not.
How $match works
The requester submits a full or partial Patient resource. The responder returns a Bundle of candidate Patient records, ordered by likelihood, each with a match score (0 to 1) and a match grade (certain, probable, or possible). The optional onlyCertainMatches parameter limits results to high-confidence matches, and count caps the number of candidates.
Pass when
  • Network B applies the CMS-approved matching logic and responds when the query matches under any specified field combination (§6).
  • Authorization is checked as well. A match alone does not oblige Network B to respond if authorization has not been granted (§6).
  • Network B accepts the authenticated $match request at the endpoint published in NPD (§5.2).
Also check at the event
  • A query that matches no combination returns no other person's data.
  • The response is a valid $match Bundle with scores and match grades.
Needs
Synthetic patients and the field combinations (test data TBD).

N2 Purpose of Use handling

Spec
§9.3 Purpose of Use Propagation. §8.1.2 (patient access request carries PATRQT). §8.2.1 (B2B requests carry purpose of use in the hl7-b2b extension).
What happens
Network A sends one query per purpose using the HL7 Purpose of Use codes below. Patient access queries carry the code in the cms_smart extension. Provider and payer queries carry it in the hl7-b2b extension.
Required codes
CodeMeaningUse case
PATRQTPatient requestPatient access
TREATTreatmentTreatment
HPAYMTHealthcare paymentPayment, including claims
CLMATTCHClaim attachmentClaim attachment within payment
HOPERATHealthcare operationsHealth care operations
HQUALIMPHealthcare quality improvementQuality measure reporting within operations
Pass when
  • Network B supports all six codes and applies the correct disclosure rules to each category (§9.3).
  • The declared purpose of use travels with the request to downstream systems (§9.3).
  • When the requester is trusted and the purpose is properly declared, neither Network B nor its participants add further authorization requirements (§9.3).
  • A patient's restrictions on which data categories an app can access are still honored, and they take precedence (§9.3, §8.1).
Also check at the event
  • A request with no declared purpose of use is rejected. The specification says every request must declare one (§9.3).

N3 Dynamic Client Registration

Spec
§7.1 Dynamic Registration. §7.2 Presumptive Eligibility. §4.2 and §4.3 (good standing, no duplicate trust gating). Terminology for Software Statement (CMS-signed) and (UDAP) in §2.
What happens
A client that is onboarded and in good standing on a home network registers with Network A, then with Network B, using the same credentials. Registration uses RFC 7591: the client sends a signed software statement to the /register endpoint as the software_statement parameter. Test with a CMS-signed software statement.
About CMS-signed statements
A CMS-signed software statement is a short-lived JWT (for example, 24-hour lifetime) signed by CMS. It asserts the client's status in a CMS registry and binds it to a verified jwks_uri. Today CMS's firmest commitment is the Medicare App Library for patient-facing apps. Use a Medicare App Library app or a CMS test statement (test issuer TBD).
Pass when
  • Both networks accept a valid CMS-signed software statement as sufficient for registration, with no additional per-network vetting (§7.1).
  • Network B registers the client without redundant onboarding or duplicate trust requirements, relying on the home network's good-standing report and the federal trust signals (§4.3, §7.1).
  • Network B lets the client operate under presumptive eligibility, 90 days by default, when the client has met its trust requirements, works in production, and is in good standing on its home network (§7.2).
  • Only operational coordination is requested (abuse contacts, rate limits, support channels) (§7.1).
Also check at the event
  • An invalid, expired, or unsigned statement is rejected.
  • A client whose home network reports it as not in good standing is not accepted (§4.2).
Still open
Whether UDAP X.509 software statements stay a required path, become optional, or are replaced by CMS-signed statements is pending Workgroup consensus (§7.1). If both networks support UDAP, you may also run this scenario with a UDAP software statement (HL7 FAST Security IG) and record it as a finding. The exact registration timeline and the handoff to presumptive eligibility are not yet specified (Appendix A, A5).
Note
Manual registration was allowed only through October 1, 2026. All participants must now support dynamic registration (§7.1).

N4 Data querying, structured and unstructured

Spec
§9.1 Respond Completely. §3.3 FHIR API Access. §3.4 Chart Notes and Clinical Documents. §4.1 Respond to queries for data holders on the network.
What happens
Network A queries Network B for a synthetic patient whose record includes encounters, USCDI v3 data, a scanned PDF, and an image. Run it after a successful N1 match, and for the declared purpose of use of your choice.
Pass when
  • The response includes all relevant data held for the patient within the use case, structured and unstructured (§9.1).
  • Structured data meets USCDI v3 (or later) and is served through FHIR APIs that follow HL7 US Core, with a complete and valid CapabilityStatement (§3.3). Labs are coded in LOINC, medications in RxNorm, and conditions in SNOMED CT.
  • Clinical documents (such as radiology reports, scanned labs, and external specialist notes) come back in human-readable formats (PDF, TIFF, or JPG) as FHIR attachments (§3.4).
  • Network B does not decline to respond only because the query came from a participant whose home network is different (§4.1).
What a response may contain
USCDI v3 is the set of data a network and its data holders must be able to return. It is not a promise that every element comes back on every call. The actual response depends on the specific query (a MedicationRequest search returns only medications), the scopes granted by the data holder's authorization server, and any limit the use case carries (a payer is limited to clinical data supporting claims from the last 60 days) (§9.1).
Should, not must
Faxes (a PDF copy where one exists) and ambient listening recordings should be returned where they exist and a standard exchange mechanism is available. There is no standard for ambient recordings yet, so don't record a missing recording as a failure (§3.4, §9.1).
Also check at the event
  • The query does not hit a dead end. Every use case should have a way to a response (§9.1).
Minimum

N5 Audit logging

Spec
§11 Audit Logging, including the IAS Audit Log API Specification (v1.0, February 2026).
What happens
After running N1 to N4, each network produces its audit log for the test queries. A home network with a patient-facing app then shows the app the audit information for that patient.
Pass when
  • Each network-mediated query has a log entry showing who accessed the data, when, the declared purpose of use, and which organizations were involved (§11).
  • Logs are at the organization level at minimum (§11).
  • The network states a retention period of at least 7 years, or longer where applicable law requires (45 CFR 164.530(j)) (§11).
  • A home network serving patient-facing apps makes audit logs available to those apps through the IAS Audit Log API, which uses FHIR AuditEvent resources and IAL2 patient authentication (§11).
Also check at the event
  • EHRs that facilitate the test queries produce audit data under the same obligations as the network routing through them (§11).
Scope limits
  • Patient-facing audit covers network-mediated queries, meaning Pathways 1 and 2. Direct queries to an NPD endpoint under Pathway 3 are excluded, because the network never sees them (§11).
  • Sharing audit events between networks is not in scope. A home network only serves the apps it onboarded (§11).
  • Retention is verified by attestation. It can't be tested in one day.

Advanced

A1 Record location (RLS)

Spec
§5.2 Record Locator Service and Pathway 2. §8.1.1 Required Precondition: Network-Mediated Record Location.
What happens
A requester sends a record-location request to Network B's RLS endpoint for a synthetic patient. For patient access, the request comes from a Medicare App Library app carrying a CMS-signed software statement and an IAL2 patient identity token from a CMS-approved identity provider.
Pass when
  • Network B's RLS endpoint is the one published in NPD, and it accepts authenticated $match requests from other CMS-aligned networks (§5.2).
  • For patient access, Network B processes the request on app authentication and IAL2 identity alone, subject to patient matching, applicable law, and security controls. The patient does not interact with the network or know which organizations hold their records (§8.1.1).
  • Network B responds for the data holders it represents, with enough information for the app to go on and retrieve data (§8.1.1).
  • Patient discovery and patient access do not depend on a bilateral agreement. Network B may require one for provider and payer queries (§5.2).
  • Record location can be started by a patient, provider, payer, or value-based care organization (§5.2).
Also check at the event
  • Follow-up queries go only to the locations the response identifies.
Still open
The wire profile of the RLS endpoint, including transport, authentication, and payload, is not yet fixed (Appendix A, A1). Retrieval can be federated (each responder serves its own data) or brokered (a network broker aggregates). Both are conformant. Brokered retrieval has no wire profile yet (A1b), so record what you used.
Note
The specification lists this as a MUST for networks (§3.2, §5.2). It is shown under Advanced here only to keep the first day manageable.
Advanced

A2 National Provider Directory publishing and usage metrics

Spec
§10 National Provider Directory Publication. §5.3 Pathway 3, Targeted Queries Against NPD. The structure, formats, and data elements are in the HTE Data Release Specifications.
What happens
The network publishes to NPD, and a second network or the test tool reads the listing back and uses it for a targeted query.
Pass when
  • The network has published its onboarded participants (apps, providers, payers, delegated tech solutions), its participants' endpoints in a form that supports targeted queries by NPI or an equivalent identifier, and its inter-network connections (§10, §5.3).
  • Usage metrics are published by participant and by use case (§10).
  • A network that onboards organizations, not individual practitioners, publishes the organization's NPI with cross-references to affiliated practitioners' NPIs where known. Where it has no affiliation data, it says so in the record (§10).
  • The listing can be read by any network, auditor, or participant to confirm an actor's listing and credentials (§10).
Still open
Trust-anchor metadata depends on the UDAP decision in §7.1 and has no concrete obligation yet (§10). The update cadence comes from the CMS Interoperability Framework. NPD has no ingestion API, so networks currently submit updates as flat files, and routine publishing at scale can't be met until one exists (Appendix A, A7).
Advanced

A3 Response for patient, provider, and payer use cases

Spec
§9.2 Use Case Coverage. §8.1 Patient Access (B2C). §8.2 Provider and Payer Access (B2B). §9.1 (no use case becomes a dead end).
What happens
Run one query per use case the network supports: patient access, provider treatment, and payer. If your network's participants engage in a use case, the network must support it (§9.2).
Pass when: patient access
  • A CMS-recognized app in good standing, acting for an IAL2-verified patient, gets patient-access tokens from data holders and retrieves data with no provider portal login and no separate developer onboarding at each data holder (§8.1).
  • The app authenticates with a private key JWT (RS384 or ES384) and the request carries the IAL2 id_token, a consent bundle, and purpose of use PATRQT. The server issues an authorization code with no login screen and no per-data-holder consent screen (§8.1, §8.1.3.1).
  • The authorization request uses POST /authorize, not GET. The token exchange uses PKCE with S256 (§8.1).
  • The data holder refuses an id_token whose auth_time is more than 300 seconds old, and refuses a reused jti and iss pair. Access tokens last no more than one hour, and refresh tokens renew on a rolling 90-day basis (§8.1.5).
Pass when: provider treatment and payer
  • Access follows SMART Backend Services with the HL7 FAST B2B profile. The requester signs a client assertion lasting no more than 5 minutes, includes the hl7-b2b extension with organization_id and purpose_of_use, and sends udap=1. The data holder returns an access token lasting no more than 60 minutes, with no refresh token (§8.2, §8.2.1).
  • A provider treatment query is answered with clinical and claims data (§9.2).
  • A payer query for clinical data supporting a claim from the last 60 days is answered as a query response, not a proactive push (§9.1, §9.2).
  • Payer quality measure queries (HQUALIMP) are answered (§9.2).
Also check at the event
  • No use case adds friction, delay, or a special process for the requester (§9.1).
Patient approval paths
The preferred path is the CMS-recognized app with IAL2 identity (Path 1). Network-level consolidated approval (Path 2) is allowed through December 31, 2026 and not after. The data holder-specific "July bridge" (Path 3) had to be sunset by November 1, 2026. By January 2027, test Path 1 only (§8.1.3). Networks and data holders must document which path they support (§8.1.4).
Still open
Prior authorization queries follow CMS-0057-F deadlines (§9.2). Credential rotation and retry policy for B2B are not specified (§8.2.1).
Advanced

A4 Honoring disclosure restrictions

GA requirement
Data Querying: networks must honor agreed-upon restrictions on disclosure (for example, 45 CFR 164.522, including out-of-pocket payment restrictions).
Spec
§9.3 (patient restrictions take precedence). §8.1.3.1, Sensitive and Restricted Data.
What happens
For a synthetic patient with a restriction on file, or an app request that carries no consent for Sensitive / Restricted Information, Network A sends a query that would otherwise return the restricted data.
Pass when
  • A patient's restriction on the data categories an app can access is honored (§9.3).
  • If the app did not ask for consent to Sensitive / Restricted Information, the Consent resource says access is denied, and the restricted data is not returned. If the token request has no positive consent, the data holder may withhold it (§8.1.3.1).
  • If the app did convey positive consent, the data holder treats it as authorization to disclose, unless law prohibits disclosure (§8.1.3.1).
  • The patient's other data is returned normally.
Also check at the event
  • A payment or operations query does not return data restricted under 45 CFR 164.522. The specification does not cite this regulation, so it comes from the GA requirement above.

Not tested at the event

  • HITRUST certification (§13). Required of every CMS aligned network, scoped to the production environment that handles PHI. Confirmed by attestation, not by a test run.
  • Rules of the Road (§16). Maintained by the HTE community. Networks are expected to adhere to them, but the attestation is still a placeholder in the specification and there's no scenario for it.
  • Appointment and encounter notifications (§12). Deferred and not in scope for initial CMS-Aligned recognition.
  • Fees and settlement (§14). Networks may not gate patient access with fees, and settlement is not appropriate for patient-directed access. Not testable in a run.
  • Pathway 4, bilateral peering (§5.4). Optional, and outside the CMS-aligned obligations.
  • Patient-contributed data (§9.4). Planned for a later phase, with write-side obligations not yet specified.
  • Electronic personal representative authentication. Not solved at the network layer in the current GA. Participants keep using their existing HIPAA-compliant processes.
